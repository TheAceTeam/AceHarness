# 代码变更报告

## 目标

把一次 AR 的最终代码差异和已有验证证据整理成开发者可以复核、复现和交接的报告。报告是证据索引，不是新的需求、设计或审查裁决。

## 输入边界

优先读取以下正式产物，并以实际仓库状态补充事实：

- `context.requirements`、`context.projectRoot` 和 CSIHarness `runId`；
- `specs/<AR-ID>/design/` 下的 `clarification.md`、`design.md`、`plan.md`、`task.md`、`design-review.md`；
- `specs/<AR-ID>/dt/` 下的 `dt-cases.md`、`dt-test-code-summary.md`、`dt-baseline-report.md`、`dt-quality-review.md`；
- `specs/<AR-ID>/implementation/` 下的 `implementation-summary.md`、`dt-test-report-post.md`、`code-review.md`、`implementation-review.md`；
- 项目实际的文件状态、代码差异和验证命令输出。

缺少的产物在报告中标记为“未提供证据/待复核”，不根据文件名或预期流程推断其内容。

## 工作方法

1. 确定 AR-ID、run-id、项目根目录和本次任务的范围围栏；上下文字段缺失时可从前置产物 frontmatter 回退，并记录回退来源。
2. 读取实施阶段记录的差异基线和 `pre_existing` 路径，再以当前仓库状态复核基线提交/时间、分支、已提交、已暂存、未暂存、删除和未跟踪内容；按生产代码、测试、配置、文档和生成文件分类，记录新增、修改、删除及关键符号。非 Git 项目保留 hash/before snapshot 的比较方式及其证据限制。未跟踪内容按 task 围栏决定是否纳入变更摘要；范围外的辅助文件记录为未纳入并说明原因。
3. 建立追踪关系：分别覆盖 FR、NFR、BR，连接需求 → design → plan/task → 变更文件或符号 → DT 用例 → 实施后结果；标明内容是本次引入还是既有行为，并为每条关系附文件路径、章节、行号或命令等可定位证据，标记已覆盖、部分覆盖、未覆盖或不适用。
4. 汇总实施后 DT 和必要回归的命令、采集时间、工具/环境版本、退出码、通过/失败数量和基线比较；明确区分已执行、未执行、历史证据和被环境阻塞的检查。
5. 汇总代码审查与实施评审的结论，分别列出已解决、接受和仍待复核的问题；保留问题 ID、证据、负责人和复现条件。逐项呈现围栏矩阵；一次性例外保留例外 ID、当前运行、精确范围、授权证据、有效期和审查结论，并明确它不改变行为、契约、任务与 DT 基线。
6. 对来源之间的范围、版本或结论冲突单独列出，区分事实、基于证据的推断和待确认项；无法证明的内容标记为待复核。
7. 提炼剩余风险、假设、兼容性/迁移/回滚注意事项，以及开发者最终复核清单。
8. 将报告写入指定路径后重新读取，确认 frontmatter、追踪表和验证证据与实际内容一致。

## 输出契约

文件：`specs/<AR-ID>/implementation/code-change-report.md`

文件使用以下 frontmatter：

```yaml
---
ar_id: <AR-ID>
run_id: <runId>
artifact: code-change-report
status: ready | blocked
updated_at: <ISO-8601>
---
```

正文按以下顺序组织：

1. 结论摘要：本次变更、目标和当前交付状态；
2. 范围、基线与工作树状态：任务围栏、基线提交/时间、分支、`pre_existing` 归因及未跟踪内容处理；
3. 文件变更清单：路径、变更类型、关键内容、影响面、围栏状态及一次性例外；
4. 需求追踪：需求、设计/任务、实现位置、DT 用例和结果；
5. 验证证据：命令、退出码、结果、基线及未完成项；
6. 证据缺口与未验证项：缺失内容、原因、责任人和解除条件；
7. 审查结论：代码审查、实施评审及问题处理状态；
8. 剩余风险与假设：证据支持的风险和明确的待复核事项；
9. 开发者最终复核清单：需确认的行为、接口、数据、测试和发布影响。

命令和结果保留足以复现的摘要，避免复制整段日志；文件链接使用项目内相对路径，行号已知时一并记录。最终行号以当前工作树为准，历史产物中的行号注明其对应版本。

当 `implementation-review.md`、`dt-test-report-post.md` 或 `code-review.md` 等工作流规定的交付证据缺失、不可读取或结论互相冲突时，报告 `status` 使用 `blocked`；报告仍记录缺口，但步骤结果使用 `fail`。只有实施评审同时为 `status: reviewed`、`verdict: pass`，且这些交付证据可核验时，报告 `status` 才使用 `ready` 并返回 `pass`。

## 职责边界

- 只整理已有证据，不新增需求、设计、任务或测试用例。
- 不修改生产代码、测试代码或既有设计产物；只创建或更新变更报告。
- 不替代代码审查或实施评审；报告如实呈现它们的结论。
- 报告状态为 `ready` 时步骤返回通过；报告状态为 `blocked` 时步骤返回失败并保留完整缺口，不能把报告已写入等同于交付已通过。
